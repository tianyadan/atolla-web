## 适用人群

| 人群 | 典型需求 | Atolla 带来的变化 |
| --- | --- | --- |
| 独立开发者 | 同时订阅多家 AI，想让它们各司其职 | 一个工作台调度三家引擎，员工各自绑定工作区 |
| 小型研发团队负责人 | 把需求拆给不同「角色」并行推进 | 人才市场预制岗位、群聊讨论、流程编排 |
| 运维 / 后端工程师 | 让 AI 帮忙查数据库、看服务，但担心误操作 | 资源集中管理、权限网关、人工审批与审计 |
| 经常离开工位的人 | 长任务跑一半需要授权 | 手机审批、iOS 灵动岛、Bark 通知 |
| 重视数据安全的团队 | 不希望代码和数据经过第三方平台 | 本机执行、自托管中继、数据库可选本地 SQLite |

## 典型场景

### 场景一：一个人的研发小队

从人才市场招聘「产品经理」「前端工程师」「Go 后端程序员」三位员工，分别绑定 Claude、Cursor 和 Codex，并各自指定工作区。你在首页把需求交给产品经理拆解，再用 `@` 让前端与后端同时给出评审意见。

### 场景二：发布前的群聊检查

把产品、前端、后端、运维四位员工拉进一个群聊，由群主主持：成员按顺序汇报构建、测试、健康检查与回滚方案，最后群主给出结论。

### 场景三：通勤路上的审批

员工在电脑上执行任务时需要安装一个依赖。你不在电脑前——手机上的灵动岛亮起，展开即可看到命令内容，点「仅本次允许」，电脑上的任务立即继续。

### 场景四：Issue 驱动的自动派单

开启 GitHub Idea 调度后，新的 Issue 会按岗位、能力标签与负载被推荐给合适的员工，进入其任务队列；执行结束后结果自动回写。详见 [3.10 GitHub Idea 调度](/docs/3-10-github-idea)。

## 不太适合的情况

- 只想要一个网页聊天机器人，不打算在本机安装任何引擎 CLI。
- 需要多租户、细粒度 RBAC 的大型企业权限体系——当前中继是单站门禁模型。
- 需要 Windows 或 Linux 桌面版——目前仍在开发中，见 [5.2 平台支持与演进路线](/docs/5-2-roadmap)。
